# レビュー観点

`develop`・`fix`・`review`のレビューは、**観点**に沿って行う。観点は「何を見るか」を書いたMarkdownのファイル1つで、レビューの役のエージェントは1つのセッションの中で観点を1つずつ順に当て、観点ごとに指摘を書く。

## 置き場所と重ね方

- masudaは14の観点を同梱している。`masuda init`は、それを対象リポジトリの`.masuda/reviews/`に書き出す
- 実行に使う観点は「同梱の観点」に「`.masuda/reviews/*.md`」を重ねたもの。同じファイル名のものは丸ごと置き換え、同梱に無いファイル名のものは足される
- ファイル名（拡張子を除く）が観点のID
- `masuda run`の時点の内容で固定され、その実行の終わりまで（`resume`しても）変わらない
- `.masuda/reviews/`をコミットしていないリポジトリでも、同梱の観点は使われる

## ファイルの形

```markdown title=".masuda/reviews/sql-migration.md"
---
name: "マイグレーションの後方互換"
trigger: "migrations/ の下のファイルを追加・変更する変更"
enable: true
---
（観点の本文。何を問題とし、何を問題としないか、指摘の書き方。レビューの役のプロンプトになる）
```

| frontmatterのキー | 意味 |
|---|---|
| `name` | 人が読む観点の名前 |
| `trigger` | 途中レビュー（`develop`のステップごとのレビュー）でこの観点を見るべき変更の条件を、自然文で書く。書かなければ、その観点は途中レビューでも常に当てられる |
| `enable` | 観点を使うかどうか。`false`ならその観点は実行に使われない。書かなければ使う |

同梱の観点を外すには、`.masuda/reviews/`の同じファイル名のファイル（`masuda init`が書き出したもの）を`enable: false`にする。frontmatterがYAMLとして読めない観点ファイルがあると、`masuda run`は定義の誤りとしてエラーで返る。

## どこで使われるか

| 場面 | 使う観点 |
|---|---|
| `develop`のステップごとの途中レビュー | レビューの役（`reviewer`）が、そのステップの差分を各観点の`trigger`に照らし、該当しない観点を飛ばす。迷ったら飛ばしてよい（見逃しは最後のレビューで拾う）。`trigger`の無い観点は飛ばさず常に当てる |
| `develop`・`fix`の最後のレビュー、`review`ワークフロー | すべての観点（`fix`には途中レビューが無い） |

レビューの後、別の役（`review-checker`）が全観点の指摘をまとめて正確かを確かめ、誤りは取り下げる。指摘は`findings`という台帳に溜まり、自動で直してよいもの（`autofix: true`）は直す役（`fixer`）がまとめて直し、別の役（`rechecker`）が解消を確かめる。fixerは実装したサブエージェントの続きとして動くので、実装の意図に照らして誤っている・計画の判断に反すると考えた指摘には、直さずに反論できる（台帳の指摘に`disputed`と理由`response`が付く）。recheckerは反論が妥当なら指摘を取り下げ、妥当でなければ直すよう戻す。取り下げられずに残った反論は、人間の判断待ちの指摘としてレポートに載る。最後にレポートを書く役が、残った指摘と直した指摘をまとめる。

レビューのセッションの数は観点の数によらない（レビューと確かめで1つずつ）。観点を増やすと、1つのセッションが長くなる。

## 落とし穴との違い

観点は、実装した**差分を判定する**ためのもの（「この差分のここが問題だ」という指摘を書かせる）。これに対して[落とし穴](settings.md#pitfalls)（`.masuda/pitfalls.jsonl`）は、実装の前に**計画へ問う**ためのもの（「この計画で、過去に踏んだこの失敗を避けられるか」という問いを立てさせる）。落とし穴は判定も修正の提案もせず、問いには計画を直す役が答え、答えられなければplan gateの前に人間に聞かれる。チームが過去に踏んだ失敗は、差分を見れば分かるものなら観点に、計画の段階で気づくべきもの（手順・順序・範囲の見落とし）なら落とし穴に書くとよい。

## 同梱の14観点

| ID | 名前 | `trigger`（途中レビューで当てる条件） |
|---|---|---|
| `comment-history-leakage` | コメントへの修正経緯・レビュー指摘の混入 | コードコメントを新規追加・変更する変更、特にレビュー指摘への対応や既存実装の修正としてコメントを書き換えている場合 |
| `dead-code` | デッドコード・未使用変数 | 関数・変数・importの削除やリネーム、条件分岐の書き換えを伴う変更 |
| `error-handling-gaps` | エラーハンドリングの漏れ | 例外処理（try/catch/except、Go言語のerr戻り値等）を新規追加・変更する変更 |
| `heavy-loop-processing` | ループ内の重い処理 | ループ処理（for/while/map等の繰り返し）を新規追加・変更する変更 |
| `implicit-type-conversion` | 暗黙の型変換・データ型不一致 | 型変換や異なる型同士の比較・演算、金額など精度が重要な数値計算を伴う変更 |
| `injection-vulnerability` | インジェクション脆弱性 | SQLクエリの組み立て、シェルコマンドの実行、HTMLレンダリング、ユーザー入力を外部システムに渡す処理を新規追加・変更する変更 |
| `input-validation-gaps` | 入力バリデーションの漏れ | 外部からの入力（APIリクエストパラメータ・フォーム入力）を受け取り処理するコードを新規追加・変更する変更 |
| `logging-secrets` | 機密情報のログ出力 | ログ出力処理を新規追加・変更する変更 |
| `missing-tests-guard-clauses` | ガード処理に対応するテストの漏れ | なし（途中レビューでも常に当てる） |
| `missing-tests-new-code` | 新規コードへのテスト漏れ | なし（途中レビューでも常に当てる） |
| `n-plus-one-query` | N+1 クエリ | ループ内でDBクエリやAPI呼び出しを行うコードを新規追加・変更する変更 |
| `nil-check-gaps` | nil / null チェックの漏れ | 外部から受け取った値（API応答・DB検索結果・Optional型・マップ/辞書からの取得結果）を扱うコードを新規追加・変更する変更 |
| `resource-leak` | リソースリーク | ファイル・DB接続・ソケット・ロックなどのリソースをopen/取得する処理を新規追加・変更する変更 |
| `secret-hardcode` | シークレット・APIキーのハードコード | APIキー・パスワード・トークン・DB接続文字列などの文字列リテラルを追加する変更 |

テストの漏れの2観点には`trigger`が無いので、途中レビューでも毎回当てられる。「テストは後のステップで書く」という計画では、途中のステップで指摘されても直せないことがある。

## 観点を書くときのこつ

- 1つの観点では1種類の問題だけを扱う。広い観点は指摘がぶれる
- 「問題としないもの」も書く。誤検知が減る
- `trigger`は差分を見て判断できる条件にする（「重要な変更」のような曖昧な書き方では当てるかどうかの判断が安定しない）
- 同梱の観点の本文が書き方の見本になる（`masuda init`で書き出したもの）
