# ADR-0047: ファイルの配置は「誰が消費するか」で決め、「masudaの動作に必要かどうか」では決めない

## Status

Accepted (2026-08-19)

## Context

本ADRは`docs/design/sandbox-workflow.md`廃止に伴う経緯の再構成である。同ドキュメントの「## リポジトリ構造」節（廃止前の188行目付近）には、実装が進むにつれて古くなったASCIIツリー自体は削除されつつも、判断軸だけは以下の一文として最後まで残っていた。

> 判断軸は「masudaの動作に必要かどうか」ではなく「誰がそのファイルを消費するか」（masuda自身の制御プロセスか、サンドボックス内で動くエージェントセッションか、ホスト側のCLIか）

この軸自体は、これまでどのADRにも独立した決定として記録されたことがない。[[0014-workspace-id-and-external-state-directory]]は「masuda自身の制御ファイルをworktree外の状態ディレクトリへ出す」という個別の結論だけを記録しており、その結論を導いた一般化可能な判断基準——「必要かどうか」ではなく「誰が消費するか」で切る——は`docs/design/sandbox-workflow.md`側にしか書かれていなかった。

この軸は0014だけの一過性の判断ではなく、その後の[[0040-per-workspace-state-daemon-for-masuda-owned-state]]・[[0043-child-mcp-server-aggregator-with-project-user-config-split]]でも、明文化されないまま同じ形で繰り返し適用されている。`docs/design/sandbox-workflow.md`が廃止されるとこの軸の存在自体が失われ、0014・0040・0043それぞれの境界線がなぜそこに引かれたのかを串刺しで説明する場所がなくなる。本ADRはその軸を独立した決定として救出する。

## Decision

ファイルをworktree内に置くか、worktree外の状態ディレクトリ（デーモンのKVストアを含む）に置くかを判断する際、「そのファイルがmasudaの動作にとって必要かどうか」を基準にしない。必要性は制御ファイルにもサブエージェント成果物にも等しく当てはまり、区別する力を持たないためである。代わりに「誰がそのファイルを消費するか」——masuda自身の制御プロセス（Go CLI・`orchestrator/*.py`）か、サンドボックス内で動くエージェントセッション（Claudeのメインセッション・サブエージェント）か——を基準にする。この軸は少なくとも次の3箇所で実際に適用されている。

1. **masuda自身の制御ファイルのworktree外配置（[[0014-workspace-id-and-external-state-directory]]）**: TASK.md・PLAN.md・INVESTIGATION.md・ゲートマーカー等は、消費者がmasuda自身（`_compute_diff`等）であり対象リポジトリの成果物ではないという理由で、`~/.local/share/masuda/workspaces/<workspace-id>/`（サンドボックスVM内では`/masuda-state`）に置かれる。worktree内に残していれば`git add -A`にmasuda自身のファイルが混入するという実害が実機で出ていた。
2. **状態デーモンへの移行境界（[[0040-per-workspace-state-daemon-for-masuda-owned-state]]）**: デーモンへ移すのは「書き手・読み手が両方ともmasuda自身のコードである」状態（`gate:*`・`internal:*`等の名前空間、`internal/gate/gate.go`・`orchestrator/*.py`が読み書きするカウンタやマーカー）だけに限定されている。`plan/summary.md`・`plan/steps.json`・`review_results/*`のように、サブエージェントが自身のRead/Edit/Bashツールで直接触る成果物は、それがmasudaのパイプライン進行に必要であってもデーモンへ移されずファイルのまま残る（`docs/design/state-daemon-mcp.md`の「デーモンへ移った状態・ファイルのまま残る状態」節に実際の一覧がある）。0040のDecisionが明記する通り、この区別は最初から正しく引けたわけではなく、`plan/summary.md`をデーモン側へ誤って移してしまい書き手と読み手が食い違うバグを実際に作っている——「必要かどうか」では区別できず「誰が消費するか」でしか区別できないことの実例である。
3. **`INSTRUCTIONS.md`が同じ理由でデーモンへ移せないこと**: `INSTRUCTIONS.md`はサブエージェントへの指示文にファイルパスそのものが埋め込まれ、内容が展開されるのではなくサブエージェント自身のReadツールで開かれる。0040のDecisionはこれを「サブエージェント向けの指示文に生のファイルパスが登場するか、それとも内容が既に文字列として展開されているか」という判断基準として明記しており、これも「消費者がmasuda自身のコードかサブエージェントか」の軸の具体化にあたる。
4. **`.masuda/settings.local.json`がクローンへ同期されないこと（[[0043-child-mcp-server-aggregator-with-project-user-config-split]]）**: 子MCPサーバーの承認・秘密情報を持つこのファイルは、`internal/worktree.syncMasudaConfig`のコピー対象から意図的に除外されている。消費者（状態デーモン、`workspace.json`の`RepoRoot`経由でrepoRootから直接読む）がworktree内で動くプロセスではないため、worktree（クローン）側に複製する必要がないという判断であり、複製すればステップコミットへ秘密情報が漏れる経路を作ってしまう。

## Alternatives Considered

- **「masudaの動作に必要かどうか」で切る軸**: `docs/design/sandbox-workflow.md`が明示的に却下していた軸そのもの。TASK.md・ゲートマーカーのような制御ファイルも、`plan/summary.md`・`review_results/*`のようなサブエージェント成果物も、どちらもmasudaのパイプラインが完走するために必要という点では同列であり、「必要かどうか」では両者を区別できない。実際、0040で問題になったのはまさにこの誤り方——`plan/summary.md`は（ゲートマーカー同様）masudaの動作に必要だからという理由でデーモン側へ寄せたくなるが、書き手がサブエージェント（masuda自身のコードではない）である以上デーモンには到達できず、ファイルのまま残す以外に選択肢がない。「必要性」を基準にすると、この区別を作れないまま実装が進み、書き手と読み手の不一致という実バグに至る。

## Consequences

- 0014・0040・0043という時期の異なる3つのADRが、それぞれ独立に見えて実は同一の判断軸の異なる適用例であることが、この軸を明文化して初めて串刺しで説明できるようになる。`docs/design/sandbox-workflow.md`廃止後もこの一貫性の説明が失われずに残る。
- 今後新しい状態・成果物を追加する際に「これはmasuda自身のコードが読み書きするか、それともサブエージェント／サンドボックス内エージェントセッションが直接触るか」を先に確認する、という再利用可能なチェックとして機能する。0040のConsequencesが既に「これは誰が書き、誰が読むか」を新しい状態を追加するたびに確認する必要があると述べているのは、この軸を（明文化されないまま）先取りしていたことの表れでもある。
- この軸は機械的に判定できるものではなく、消費者の同定を誤ると0040で実際に起きたように書き手・読み手の不一致というバグに直結する。軸を言語化したこと自体が誤りを防ぐわけではなく、適用のたびに個別の確認が必要という点は変わらない。
- 本ADRはコードや挙動を一切変更しない。既に存在する3件の決定に共通する判断基準を、その名を持たないまま散在していた状態から、参照可能な1つの決定として独立させるだけのものである。
