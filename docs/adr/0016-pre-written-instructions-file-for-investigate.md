# ADR-0016: `plan start --file`で事前準備済みの指示書をフェーズ1に渡し、ファクトチェックさせる

## Status

Accepted (2026-07-27)

## Context

`masuda plan start <branch> "<task>"`のtaskは1行のプレーンテキストのみで、事前にある程度調査を進めていた場合にその内容（修正指示書等）をフェーズ1（調査）に渡す手段がなかった。以前の会話では「`masuda plan chat`で対話中に対話でINVESTIGATION.mdを手動で書き込ませる」という非公式の回避策を案内したことがあったが、ユーザーからこれをCLIの正式機能にしたいという要望があった。

ここで重要なのは、ユーザーの要望が単に「指示書の内容をそのまま調査の前提として使わせたい」ではなく、「この指示書の内容に問題がないかを確認したうえでプランを提示してほしい」だったこと。つまり指示書を盲信させるのではなく、実際のコードベースと突き合わせて検証させることが目的。

## Decision

`masuda plan start`に`--file <path>`フラグを追加する（新規ワークスペース作成時のみ有効。既存ワークスペースの再開時にはtaskと同様に受け付けずエラーにする——再開時には追加の入力を渡す経路がそもそも無いため）。

指定されたファイルの内容は、投入された時点で状態ディレクトリに`INSTRUCTIONS.md`としてスナップショットコピーする（`.masuda-task.md`にtaskの文字列をコピーする既存の`WriteTaskBrief`と全く同じパターン）。元ファイルへの絶対パスをその都度参照するのではなく、開始時点の中身を独立してコピーする。

`orchestrator/investigate_plan_graph.py`の`_investigate_task`は、`INSTRUCTIONS_MD`が存在する場合のみ、investigatorサブエージェントへの指示に「この指示書を読み、コードベースと矛盾しないか・実現可能かを検証し、問題があればINVESTIGATION.mdの『指示書の検証結果』節に具体的に指摘せよ」という一文を追加する。フェーズ2（プラン作成）は無変更——プランエージェントは既存通りINVESTIGATION.mdの全文を読むため、検証結果も自然にプランへ反映される。

investigatorサブエージェントのRead権限は既に無制限（`internal/hostloop.customAgentsJSON`のTools一覧・`allowedTools`いずれもReadにパス制限を付けていない）なので、状態ディレクトリ配下の絶対パスをプロンプト文中に埋め込むだけで良く、追加の権限設定は不要だった。

## Alternatives Considered

- **元ファイルへの絶対パスをそのまま参照させ、コピーしない**: Go側の実装が一行減るが、開始後に元ファイルが編集・移動・削除されると挙動が変わってしまい、`.masuda-task.md`が既に確立している「開始時点でスナップショットする」という規約とも矛盾するため不採用。
- **指示書の内容をそのまま無条件に信頼して調査・プランに使う**: ユーザーの要望の核心（「問題がないか確認」）を満たさないため不採用。
- **検証結果が「問題あり」だった場合に専用の構造化シグナル（`needs_more_investigation`のような）でブロックする**: 既存のG1（プラン承認ゲート）で人間がPLAN.mdを見て判断する既存フローで十分カバーできる（検証結果はINVESTIGATION.md経由でPLAN.mdに反映され、G1で人間が確認する）ため、専用の新しいゲート機構は不採用。

## Consequences

- `_investigate_task`のTASK.md出力に、`INSTRUCTIONS_MD`の有無で分岐する追加セクションが入るようになった。既存のPythonテストは全て部分文字列一致のみで完全一致を見ていないため、この変更で既存テストへの影響はなかった
- `masuda plan show`は`INSTRUCTIONS.md`の内容を表示しない（G1で見るのはあくまでPLAN.md、そこに検証結果が反映されている前提）。指示書そのものを人間が直接読み返したい場合は状態ディレクトリを直接見る必要があり、今回はその導線までは整備していない
