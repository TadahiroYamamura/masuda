# ADR-0050: 現在の設計は`docs/design/`が、判断の経緯は`docs/adr/`が持ち、CLAUDE.mdはどちらも持たない

## Status

Accepted (2026-08-19)

## Context

CLAUDE.mdは毎セッション全文がコンテキストへロードされるが、27,671文字（ADR番号への参照28箇所）まで肥大していた。さらに冒頭の「作業を始める前に読むもの」が`docs/adr/0001`〜`0028`の通読を指示しており、日本語のADR本文は44本で289KBあるため、指示に愚直に従うと作業開始前に10万トークン以上を消費する状態だった。

肥大の原因は個々の記述が不要だったからではなく、**書き足す先の判断基準が無かった**ことにある。「なぜこの実装を選んだか」「この機構はどう動くか」「このファイルにはこういう罠がある」がすべてCLAUDE.mdへ流れ込み、`docs/design/sandbox-workflow.md`（当時の唯一の設計ドキュメント）も経緯4割・陳腐化6箇所という混合状態になっていた。結果として「現在何がどう動いているか」を知りたい読者が信頼して開ける場所が存在しなかった。

`adr-author` skillはこの流入を止めるために既に存在していたが、発火条件が「ADRを書くとき」に限られており、事実を書き足すだけの場合や、既存ADRのStatusを保守する場合には起動しなかった。

## Decision

プロジェクトの記憶を5つの置き場所に分け、それぞれの役割と「いつ読まれるか」を固定する。

| 置き場所 | 役割 | 読まれる瞬間 |
|---|---|---|
| `CLAUDE.md` | オリエンテーションとルーティング | 毎セッション冒頭、全文 |
| `docs/design/` | 現在の設計。現在形のみ | その部分を触る直前、トピック単位 |
| `docs/adr/` | 判断の経緯と却下した代替案 | 「なぜ」を問われたとき、番号単位 |
| コードコメント | そのファイル固有の罠・制約 | そのファイルを開いているとき |
| コミットメッセージ | 起きたことの記録 | 変更の経緯を追うとき |

判断基準は「**読まれる瞬間に、その読者が何を開いているか**」。CLAUDE.mdは毎セッション支払われるので、特定の後の瞬間にしか要らないものは置かない——理由もADR番号も、特定領域の罠も。

これを次の形で実装する。

- **`docs/design/`をコードの部分系ごとに分割する。** 構成はCLAUDE.mdの見出しではなくコードから導出する（見出しから導くと、CLAUDE.mdが手薄な部分系に構造上ずっと行き場が無い）。全ソースファイルがいずれかのドキュメントに対応することを条件にする
- **`docs/adr/`の本文は凍結し、`## Status`欄だけを更新可能とする。** 語彙は`Accepted` / `一部改訂:`（後続の決定が一部を置き換えた） / `訂正:`（書かれた時点から事実として誤っていた） / `Superseded by`（全体が無効）の4つ
- **`docs/adr/README.md`を唯一の入口とする。** `Superseded by`になったADRは索引から行ごと削除する（ファイルは残す）
- **改訂の記録先は2箇所に固定する。** ADRのStatus欄（何がどう変わったか）と索引行（番号のみ）。3箇所目を作らない
- **経緯へのポインターは`docs/design/`に置き、CLAUDE.mdには置かない。** コードコメントに置くのも可
- **`doc-placement` skillを振り分けのゲートとする。** 発火条件を「CLAUDE.mdや`docs/design/`に内容を追加しようとしているとき」「トレードオフを書きかけたとき」「どこに属するか迷ったとき」まで広げる

## Alternatives Considered

- **判断基準を`docs/adr/README.md`に置く**: 最初に実装した形。ADRディレクトリを開いた後にしか読めないため、「開くべきか」の判断には間に合わない。ゲートはゲートの手前に置く必要がある
- **索引に`Superseded by`のADRも残す**: ADR運用としてはこちらが一般的で、無効化された決定が一目で分かるという利点がある。採らなかったのは、この索引の役割が「どれを開くか」の判定に特化しているため——二度と開く必要のないものを載せると、判断コストを毎回払うことになる。到達経路は覆した側のADRからの`[[...]]`リンクで足りる
- **ドキュメントの役割分担をCLAUDE.mdにも明記する**: skillが発火しなかった場合の受け皿として検討したが、採らなかった。コンテキストが積まれた後はセッション冒頭の情報の想起率が落ちるため、コード編集を経た後の「書き足す瞬間」には効きにくい（ユーザーの運用経験による）。skillで拾い、漏れたら人間が指摘する運用にする
- **CLAUDE.md編集時にフックで強制する**（`.claude/settings.json`の`PreToolUse`）: 唯一決定的に発火する手段。masudaを自分自身に対して回すとき、サンドボックス内のエージェントも同じ設定を読むため、ブロックする実装だと無人ループが確認待ちで停止する。散文の規約で運用して不足が確認できてから検討する
- **`.claude/rules/`に`paths:`付きで置く**: 指定パスに触れた時点でロードされるため、skillのdescriptionベースより確実に発火する。masudaのサンドボックス内でプロジェクトレベルの`rules/`が読まれるかが未検証（Issue #37）のため、検証後に再検討する

## Consequences

- CLAUDE.mdは27,671文字から2,234文字になり、ADR番号への参照は0になった。ADR通読の指示も消えたため、起動時のコンテキスト消費は実質ゼロになる
- `docs/design/`は15ファイル（README含む）になった。1トピックを読むコストは数千トークンで、必要なトピックだけを開ける
- **書き足すたびに置き場所の判断が要る。** 迷いなく1箇所へ書けた以前より、書く側のコストは上がる。`doc-placement` skillはこのコストを下げるためのものだが、skillが発火しなかった場合は誤った場所に落ちる
- **改訂の記録が2箇所に分かれる。** ADRを1本書くたびに、覆される側のStatus欄と索引行の両方を更新する必要がある。`adr-author` skillのB-2に手順と検証コマンドを置いたが、忘れれば索引が信用できなくなる
- ADR本文を凍結したため、本文に残る誤り・陳腐化した参照は直せない。`訂正:`はこの制約への対処だが、読者はStatus欄を必ず読む必要がある
- 設計ドキュメントが参照する行番号は、隣接する変更で容易にずれる。実際にこの整備の直後、developのマージで`Dockerfile`が3行伸びただけで3箇所がずれた
- masudaは複数ブランチ・worktreeで並行開発されるため、ADR番号は自分のブランチだけを見ると衝突する。実際にこの整備中、別ブランチの未pushコミットが同じ番号を使っており、4本を繰り下げた
