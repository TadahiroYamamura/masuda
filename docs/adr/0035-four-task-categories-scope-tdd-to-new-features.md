# ADR-0035: masudaが扱うタスクを検証可能性・解法既知性・リスクの3軸で4カテゴリに分類し、TDDモードの対象を「新機能追加」カテゴリに限定する

## Status

Accepted (2026-08-06)

## Context

Issue #3（TDD開発モードのサポート）は「バグ修正では現状の実装フローで満足しているが、新機能追加ではTDD（red→green→refactor）で実装してほしい」という要望を出発点にしていたが、TDDモードの指定方法・commit粒度・既存スキル流用可否という3つの論点が未決定のまま残っていた（Issue本文の「未決定の論点」）。これらを検討する前に、そもそも「バグ修正」「新機能追加」というラベル自体がmasudaの扱うタスク全体をどれだけ正しく切り分けているのか（他に見落としているユースケースがないか）を確認する必要があった。

最初に一般的なソフトウェア開発のタスク分類（バグ修正・新機能追加・リファクタリング・依存更新・パフォーマンス改善・セキュリティ修正・ドキュメントのみ・大規模移行・テスト追加のみ・調査のみ）を経験則で列挙したが、この列挙はMECEではなかった（例: 「大規模移行」は「リファクタリング」の規模違いに過ぎず、「新機能追加」を「テスト先行」で作れば同時に「TDD」の性質も持つ、といった重複が生じる一方、列挙を続ける限り漏れの余地も消えない）。

次にmasudaのパイプライン各フェーズ（調査/プラン/G1/実装ループ/レビュー/G2）を歩き、「振る舞いが変わりうる点」を軸候補として抽出する方法を試みたが、これは[[0027-phase4-step-based-implement-review-commit-loop]]等が既に定義した実装パラメータを再列挙しているだけで、タスク自体の性質から独立して導いた軸になっておらず、意味のある分類に至らなかった。

## Decision

タスクという概念そのものの性質（masudaの実装の都合とは独立）から軸候補を出す方式に転換し、以下の3軸でタスクを分類する。

- **B: 検証可能性の性質** — 完了をどう判定できるか。値は「自動テストで二値判定可能」「定量計測が必要」「自動検証不可能で人間の主観判断のみ」の3つ
- **C: 解法の既知性** — 着手前にどれだけ解法が分かっているか。値は「定型・機械的」「探索的（設計判断を伴う）」の2つ
- **F: リスク・可逆性** — 間違えた場合の影響範囲。値は「ローカルで完結し戻しやすい」「外部・本番・セキュリティに影響し戻しにくい」の2つ

軸として採用する判定基準は「その軸の値が変わるとmasuda上の作業のやり方が実際に変わるか」とした。この基準で当初の6軸候補（A: 挙動保存性、B、C、D: テストとの関係性、E: 成果物の種類、F）のうちAとEを不採用にし（Alternatives Considered参照）、Dは独立軸ではなくBのサブ軸（Bが「自動テスト可能」または「定量計測」の値を取るときのみ意味を持つ、テスト先行/後追い/不要の3値）として扱うことにした。

軸の独立性は、2軸ずつのマトリクスを組み各セルに実在しうる具体例が埋まるかで検証した（C×F・D×F・C×Dは共に高い充填率で独立性を確認、B×Dは「B=主観判断のみ」の行でDの3値が実質「不要」の一択に潰れることが分かりサブ軸と判定）。

B×D（行）×C×F（列）の24マスのマトリクスを組んだ上で、masudaが価値を出せない・出しにくいユースケースを以下の基準で除外した。

1. **B=定量計測×F=高リスク（本番影響）**: masudaはDockerサンドボックス＋ローカルworktreeで完結し、pushも常に手動でデプロイは範囲外（[[0005-manual-push-automatic-worktree-ops]]）、本番トラフィック・APM・実データ規模へのアクセスがない。定量計測タスクの完了判定自体が本番相当の負荷・データを要する場合、検証ループがmasudaの手の届かない場所に丸ごと移ってしまうため対象外
2. **B=主観判断のみ**（ドキュメントのみの変更が中心）: (1)とは異なり構造的にできないわけではないが、masudaの価値の源泉（Dockerサンドボックス起動、[[0009-implementation-self-verification-loop]]のビルド/テスト自己検証ループ、LSPベースのレビュー）が、成果物がprose中心でコンパイル・テスト可能な対象を持たない場合は一切働かせる場面がなく、機構が空回りするため対象外
3. **D=不要×F=高リスク**: 本当に本番影響が大きく戻しにくいなら、変更自体が定型的でも検証を求めるのが自然という理由で、この組み合わせは実質成立しないと判断し除外

以上の絞り込みにより13マスが残り、これをB×D（行）でグルーピングするとC×F（列）はカテゴリ内の変動要因に過ぎないことが分かり、以下4カテゴリに整理できた（セル数の内訳も過不足なく一致）。

| カテゴリ | B×D | セル数 | 備考 |
|---|---|---|---|
| ごく軽い修正 | 自動テスト可能×テスト不要 | 1 | 例: 些細な定数変更・typo修正 |
| バグの修正 | 自動テスト可能×テスト後追い | 4 | masudaの現状のデフォルトフロー |
| 新機能の追加 | 自動テスト可能×テスト先行 | 4 | Issue #3のTDDモードが対応するカテゴリ |
| パフォーマンス改善 | 定量計測（ローカル完結のみ） | 4 | 今回新たに識別。masudaはまだ対応方法を設計していない |

「バグの修正」と「新機能の追加」は現状どちらも同じ点（B=自動テスト可能×D=後追い）にある。Issue #3が求めているのは、新機能追加カテゴリだけをD=テスト先行に固定できるようにする仕組みであり、バグ修正はD=後追いのまま変えない。

この分類を、Issue #3のスコープ確定（新機能追加カテゴリのみを対象とし、バグ修正・軽い修正のフローは変更しない）およびmasudaの今後のタスク分類の基準として採用する。「パフォーマンス改善」カテゴリはIssue #3のスコープに含めず、別Issueとして切り出す。

## Alternatives Considered

- **経験則によるフラットなユースケース列挙**（バグ修正/新機能追加/リファクタリング/依存更新/パフォーマンス改善/セキュリティ修正/ドキュメントのみ/大規模移行/テスト追加のみ/調査のみ）: 「タスクの意図」「成果物の種類」「変更規模」という異なる次元を無自覚に混ぜた分類になり、重複（新機能追加をテスト先行で作ればTDDでもある、大規模移行はリファクタリングの規模違い等）と漏れ（列挙を続ける限り解消しない）が両方生じるため不採用
- **masudaのパイプライン各フェーズを歩いて軸候補を抽出する方法**: 各フェーズで「振る舞いが変わりうる点」を機械的に洗い出す方法を試したが、これは既存実装（[[0009-implementation-self-verification-loop]]・[[0027-phase4-step-based-implement-review-commit-loop]]等）が持つパラメータの再列挙に留まり、タスク自体の性質から独立して導出した軸にならず、分類として意味を持たなかったため不採用
- **軸A（挙動保存性: 外部から見た挙動を変えるか否か）の採用**: 「挙動保存タスクは作業のやり方が変わる」という主張を分解すると、実質的にB（既存テストを安全網として使う）とD（新規テストを書かない）の特定の値の組み合わせに還元でき、B・Dとは独立に作業のやり方を変えている部分が見当たらなかったため不採用
- **軸E（成果物の種類: コード/ドキュメント・設定/データ・スキーマ）の採用**: 「具体例が思いつくか」で判定すると3×3マトリクスの9マス全てに実在しうる例が埋まり独立軸に見えたが、「masudaの処理が実際に分岐するか」まで基準を厳しくすると、[[0009-implementation-self-verification-loop]]の自己検証ループ（対象がgo testでもdocker buildでもmasuda側の処理は同一）に吸収されることが分かり不採用。「具体例が埋まるか」だけでは軸の独立性検証として不十分で、「masudaの処理が実際に分岐するか」まで問う必要があるという教訓が得られた
- **軸D（テストとの関係性: テスト先行/後追い/不要）の独立軸としての採用**: B×Dのマトリクスで「B=主観判断のみ」の行ではDの3値が実質「不要」の一択に潰れ、Dが独立した選択肢を持つのはB=自動テスト可能／定量計測のときだけと判明したため、独立軸ではなくBのサブ軸として扱うことにした

## Consequences

- Issue #3のTDDモード実装は「新機能追加」カテゴリに対象を限定してよく、バグ修正・軽い修正のプロンプト/フローを変更する必要がない
- 「パフォーマンス改善」（B=定量計測、ローカルで完結する場合のみ）という、これまでmasudaが想定していなかったユースケースが新たに認識された。対応方法（完了条件をビルド/テストgreenではなく計測結果の改善で判定する仕組み等）は本ADRのスコープ外で、別Issueとして起票が必要
- B=定量計測×F=高リスク（本番相当の環境が必要な性能検証）およびB=主観判断のみ（ドキュメントのみの変更）は、今後masudaの適用範囲から意図的に除外されたユースケースとして扱われる。将来これらへの対応を検討する場合、本ADRの除外理由（サンドボックスから本番環境への到達不能性、ビルド/テストループの空回り）を踏まえた別の設計が必要になる
- この4カテゴリ分類・3軸（B・C・F、DはBのサブ軸）は今後masudaがタスクの性質を議論する際の共通言語になる。ただし軸の網羅性は「パイプライン各フェーズを歩く」「経験則で列挙する」のいずれとも異なる第三の方法（タスクという概念の性質から独立に軸候補を出し、2軸マトリクスで独立性を検証する）で得られたものであり、新しい軸候補が出た場合も同じ検証手順（具体例の充填率確認→処理が実際に分岐するかの確認）を踏むことが望ましい
