# ADR-0028: プラン段階で予想する副産物ファイルパターンを、機械的バックストップの除外対象にする

## Status

Accepted (2026-08-04)

## Context

[[0027-phase4-step-based-implement-review-commit-loop]]でフェーズ4をステップ単位の
commitに変えた後、実機（Dockerサンドボックス、トイプロジェクト）で検証したところ、
ビルド/テストの自己修正ループ（[[0009-implementation-self-verification-loop]]）が
`pytest`を実行した副作用で`__pycache__/*.pyc`が生成され、これがステップの宣言
ファイル一覧に含まれていないため[[0010-plan-deviation-reopens-plan-gate]]の機械的
バックストップに引っかかり、G1が再オープンされる事象が実際に発生した。

ADR-0027はこの種の副産物を「commit対象からは除外するが、作業ツリーには残り続け、
最終的にはフェーズ5のdiff計算やG2承認時の最終commitに混入しうる」既知の限界として
記録していたが、`changed_files`（commit対象を絞り込む自己申告）とは別に、バック
ストップの逸脱判定そのものから副産物を除外する手段までは持っていなかった。

除外判定に何らかの自己申告を使う案も検討したが、[[0010-plan-deviation-reopens-plan-gate]]
の「自己申告に頼り切らない」という核心的な保証と衝突する。**実装**サブエージェントが
実装後に「これは副産物だから無視してよい」と申告する形にすると、スコープ逸脱を
「ただの副産物」と偽って通せてしまうリスクを再び持ち込むことになるため、この形は
不採用とした。

一方で、**プランナー**が実装前に「このプロジェクトのビルド/テストツールはこの
パターンのファイルを生成しうる」と予想し、その予想が[[0008-investigate-plan-agent-separation-with-redo]]
のG1で人間にレビュー・承認されるなら、話は変わる。この予想は`plan/steps.json`の
`files`（変更するファイル一覧）と全く同じ信頼レベルのデータになり、実装エージェント
がこの予想を事後に書き換える余地はない（G1承認時点で固定される）。

## Decision

`plan/steps.json`の構造をステップの配列から、ステップ配列と副産物パターン配列を
持つオブジェクトに変える。

```json
{
  "steps": [ { "description": "...", "files": [...] }, ... ],
  "expected_byproducts": ["**/__pycache__/**", "**/*.pyc", "merged.yaml"]
}
```

`expected_byproducts`はグロブパターンの配列。追跡済みファイルが副作用で書き換わる
ケース——ユーザーから実例として挙がった、OpenAPIコード生成で更新される
`merged.yaml`——と、未追跡の生成物が新規に現れるケース——今回実機で再現した
`__pycache__`——の両方を1つの仕組みでカバーする。プランナーは調査（フェーズ1）で
判明したプロジェクトのビルド/テストツールチェーンの挙動から、生成されうるパターンを
予想して書く。予想が無ければ空配列でよい。

パターンの評価は標準的なglob記法（シェルや`.gitignore`と同じ、`*`は`/`をまたがず
`**`はまたぐ）に自前で対応する`_glob_to_regex()`を新設して行う。標準ライブラリの
`fnmatch`は単独の`*`が`/`もまたいでしまい、多くのエンジニアの直感に反する挙動になる
ため使わない（実装時、`fnmatch`ベースの初版で`*__pycache__*`のようなパターンが
意図せず`**/__pycache__/**`相当の広いマッチになっていたことが判明し、書き直した）。

`orchestrator/implement_review_graph.py`の`_extra_changed_files()`（ADR-0010の
バックストップが使う「計画外の変更」集合を計算する関数）は、`_actual_changed_files()`
の結果から`expected_byproducts`のいずれかのパターンにマッチするパスも追加で除外する。
既存の`_read_approved_deviations()`（人間が事後承認した逸脱の記録）と同じ「除外
リスト」の扱いだが、こちらは実装前に人間が承認済みという点が異なる。

`masuda plan show`（`internal/gate/gate.go`のrenderPlan）は`expected_byproducts`が
空でなければ「## 生成される可能性のある副産物ファイル」として一覧表示し、G1で
人間が予想の妥当性も確認できるようにする。

**クリーンアップは行わない**: 除外判定にのみ使い、マッチしたファイルを実際に
削除する自動クリーンアップは今回のスコープに含めない。作業ツリーに残り続けて
G2の最終diffに混入しうるという[[0027-phase4-step-based-implement-review-commit-loop]]
の既知の限界は、この変更後も残る。理由は代替案を参照。

## Alternatives Considered

- **標準ライブラリの`fnmatch`でパターンを評価する**: 実装コストが最小で済むため
  最初はこれを採用したが、単独の`*`が`/`もまたいでしまうという挙動は一般的な
  シェルglobや`.gitignore`の感覚と食い違い、パターンを書く人間（プランナーの
  出力をG1でレビューする人間を含む）の直感に反する。`*__pycache__*`が実際には
  `**/__pycache__/**`相当の意図しない広さでマッチしてしまう問題が実装時に見つかり、
  不採用に切り替えた。
- **実装エージェントの事後申告（`changed_files`と対になる`ignored_files`）で除外する**:
  検討したが、実装エージェント自身の申告を逸脱検知の判定に使うことになり、
  [[0010-plan-deviation-reopens-plan-gate]]が「自己申告に頼り切らない」としている
  理由がそのまま当てはまる。スコープ逸脱を副産物と偽って通せるリスクを避けるため不採用。
- **既存の`.gitignore`に頼る**: `.gitignore`されていれば`git status`はそもそも
  未追跡の副産物を拾わないため、多くのケースでは追加の仕組みが不要になる。しかし
  ユーザーが実例として挙げた`merged.yaml`（追跡済みファイルが副作用で書き換わる
  ケース）には`.gitignore`が効かない（gitは追跡済みファイルの変更を無視設定に
  関わらず常に報告する）ため、このケースをカバーできず不採用。今回の仕組みは
  `.gitignore`を置き換えるものではなく、`.gitignore`が効かない場面を補うもの。
- **マッチしたファイルを自動クリーンアップ（削除）する**: 除外判定と同時に実装する
  案も検討したが、削除は破壊的操作であり、パターンの予想が不正確だった場合に
  意図しないファイルを消すリスクがある。今回は除外判定のみにとどめ、クリーンアップは
  別途必要性が明確になってから検討する。
- **`plan/expected_byproducts.json`という別ファイルにする**: `plan/steps.json`の
  形を変えずに済むが、[[0026-plan-md-as-prose-plus-per-step-json]]で「プランの
  機械的データは1ファイルにまとめる」という設計にした直後に3ファイル目を増やすのは
  一貫性を欠く。`steps`と`expected_byproducts`はどちらも「プランナーが予想し人間が
  承認する構造化データ」という同じ性質を持つため、同じファイルにまとめる方が自然と
  判断した。

## Consequences

- `plan/steps.json`を読むすべてのコード（Go側`internal/gate`・Python側
  `orchestrator/implement_review_graph.py`・`orchestrator/investigate_plan_graph.py`）
  が、配列直下ではなく`{"steps": [...], "expected_byproducts": [...]}`という
  オブジェクトを前提にする必要がある（破壊的変更、ADR-0026と同じく後方互換は用意しない）
- プランナーは投資調査の段階で、ビルド/テストツールチェーンが生成しうる副産物
  パターンまで見積もる責任を持つことになる。見積もりが不正確（パターンが狭すぎる）
  でも実害はない——単に今まで通りG1再オープンで人間が都度判断するだけであり、
  安全側に倒れた失敗モードになる
- 追跡済みファイルの副作用変更（`merged.yaml`パターン）と未追跡の新規生成物
  （`__pycache__`パターン）を同じ仕組みで扱えるようになった
- クリーンアップを行わないため、承認された副産物は作業ツリーに残り続け、フェーズ5の
  `_compute_diff()`やG2承認時の最終commitに混入しうるという既知の限界は解消していない
