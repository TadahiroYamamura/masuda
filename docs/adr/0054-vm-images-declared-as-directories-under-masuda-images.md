# ADR-0054: VMイメージは`.masuda/images/<name>/`のディレクトリ単位で宣言し、`settings.json`の`image`はそのエントリ名を指す

## Status

Accepted (2026-08-20)

## Context

[[0015-native-lsp-plugins-and-repo-declared-image]]が「使用するイメージの選定は対象repo側の責任」という原則を確立し、[[0032-masuda-self-update-via-github-release-and-dockerhub-pull]]が`.masuda/Dockerfile`（固定パス、`masuda init`が雛形を実体化し、`masuda update`がFROM行を書き換える）を追加した。この時点でイメージに関する情報は2箇所に分かれている——イメージの中身は`.masuda/Dockerfile`、実行時にどのイメージを使うかは`.masuda/settings.json`の`image`（ビルド済みローカルDockerタグ名）。

ここに2つの圧力が同時に加わった。

1つ目は[[0053-privileged-commands-declared-and-run-in-disposable-vm]]が導入する2種類目のVMイメージである。特権操作用の使い捨てVMは、メインサンドボックスVMとは別のイメージを必要とする。ADR-0053を起草した時点では「メインVM用の`Dockerfile`とは別に、専用VMイメージ・ライフサイクルを新たに保守する」前提だったが、それはイメージの管理方法が2系統に分岐することを意味していた。

2つ目はrootfsサイズを指定する経路が存在しないことである。Issue #31の実機検証で、`internal/rootfs.Build`のサイズ計算（tar実サイズ+20%+固定マージン、下限あり）が完全自動であり外部から上書きできないため、Docker一式（展開後約226MB）を積むだけで空き容量が逼迫することが判明した。サイズはイメージの中身で決まる値だが、置き場所の候補（トップレベルの`settings.json`、あるいはADR-0053の特権コマンド宣言）はいずれもイメージそのものではないため、メインVM用と特権VM用でサイズの宣言箇所が割れる。

さらに、ADR-0053の承認機構には`image`がタグ名であることに由来する穴がある。承認は宣言（コマンド・イメージ・タイムアウト）のハッシュに固定されるが、`image`が指すのは不透明なタグ名であり、そのタグの中身が後から変わっても承認は生き残る。特権付きで実行されるものを承認が完全に覆えていない。

## Decision

イメージ1つを1ディレクトリとして宣言する。

```
.masuda/
  settings.json                 # image: "default" ——どのエントリを使うか
  images/
    default/                    # メインサンドボックスVM
      Dockerfile
      settings.json             # このイメージのビルドパラメータ
    <name>/                     # 特権コマンド用など、追加のエントリ
      Dockerfile
      settings.json
```

- **`.masuda/settings.json`の`image`フィールドと`--image`フラグは、`.masuda/images/`配下のエントリ名を指す**。ADR-0015・ADR-0032の「ビルド済みローカルDockerタグ名」という意味論を変更する。ローカルDockerタグはmasudaがエントリ名とリポジトリの同一性（`repoRoot`の絶対パスから導くハッシュ）から導出する内部的な値になり、ユーザーが目にする識別子ではなくなる。タグにリポジトリ由来の成分を含めるのは、複数の対象リポジトリが同じエントリ名（`default`）を使ったときにローカルタグが衝突するのを防ぐため——`image`がタグ名だった従来はこの衝突が利用者の命名責任だった
- **エントリ名は`[a-z0-9][a-z0-9-]*`に制約する**。導出するDockerタグとして正当であることと、エントリ名がファイルパスの構成要素として使われる（ディレクトリ名、およびADR-0053の実行結果ディレクトリ）ことの両方に必要
- **`.masuda/Dockerfile`は読まない**。移行のためのフォールバックも持たない（[[0024-file-based-perspectives-mechanical-checker-prompt]]が`.masuda.json`→`.masuda/settings.json`で採った破壊的変更と同じ扱い）
- **イメージごとの`settings.json`はビルドパラメータを持つ**。第一のフィールドはrootfsサイズの上書き。Go側の型名は`config.ImageConfig`とし、トップレベルの`config.Config`と混同しない名前にする
- **`internal/rootfs.Build`はサイズを引数で受け取る**。指定値は「置き換え」ではなく**下限**として扱い、自動計算値との大きい方を採る。中身より小さい値を指定された場合に`mkfs.ext4`が失敗するか、起動直後に空き容量のないVMができるだけであり、指定値をそのまま使う意味がないため。上限はmasuda側の定数として持ち、超過する宣言はエラーにする——`.masuda/`配下は対象リポジトリがコミットするファイルであり（Issue #19）、これまでの宣言的フィールドがいずれも「サンドボックスの中で何が起きるか」しか変えなかったのに対し、rootfsサイズは初めてホスト側のディスクを直接消費する数字になる。`mkfs.ext4`は疎ファイルを作るがinodeテーブル等のメタデータは実書き込みされるため、桁を誤った宣言は承認前に止める必要がある
- **`masuda init`は`default`エントリだけを実体化し、2つ目以降は`masuda image add <entry> [--template ...]`で明示的に作る**（ADR-0024・[[0031-claude-settings-field-init-materialized-no-implicit-default]]・ADR-0032と同じmaterialize方式）。宣言された全エントリは`masuda update`がビルドするため、initが特権コマンド用のイメージまで作ると、特権コマンドを一度も使わないプロジェクトが毎回そのビルド（Docker入りで600MiB超）を負担することになる。ADR-0053が`Image`を必須フィールドとし暗黙のフォールバックを持たないと決めたのは、この実体化と対になっている——宣言が指す名前は、ユーザーが見る・編集する・コミットするディレクトリとしてリポジトリ内に必ず存在する
- **テンプレートはCLIバイナリに埋め込む**（`assets.go`）。観点ファイル（[[0033-perspective-enable-flag-and-release-asset-sync]]）はGitHub Releaseアセットとして配るが、あれは`masuda update`実行中のプロセスが旧バイナリのままであるために埋め込みだと反映が1リリース遅れる、という理由による。テンプレートを読むのはユーザーが単独で叩くコマンドで、その時点のバイナリは既に更新後のものであるため、この問題は起きない
- **`masuda update`のFROM行書き換えは`.masuda/images/*/Dockerfile`の走査に一般化する**。masuda自身のbaseイメージを参照しない行に触らない従来の挙動（`internal/selfupdate.UpdateDockerfileFromTag`）はそのまま——特権VM用イメージのようにmasudaのbaseから派生しないエントリは、走査対象に入っても書き換えられない
- **ワークスペースのcloneへは同期しない**。[[0036-sync-uncommitted-masuda-config-into-clone]]が`.masuda/Dockerfile`を許可リストから外したのと同じ理由（イメージのビルドは常に`repoRoot`基準で行われ、cloneの中身が参照されることはない）がそのまま当てはまる
- **イメージごとの`settings.json`に、実行結果として回収するファイルの宣言は置かない**。回収の対象はイメージではなくコマンドごとに変わるため、それはADR-0053の`PrivilegedCommandDecl`側の宣言である。イメージ定義の側からこの経路を開けてはならない

この形により、ADR-0053の承認はイメージディレクトリの内容（`Dockerfile`とイメージ側`settings.json`）のダイジェストを承認ハッシュに含められるようになる。特権付きで実行されるものの全体——コマンド、それが走るイメージの中身、ビルドパラメータ——が1つの承認で覆われる。

## Alternatives Considered

- **`image`を従来どおりタグ名のままにし、イメージごとの`settings.json`に`tag`フィールドを持たせる**: 破壊的変更を避けられるが、「エントリ名」と「タグ名」という2つの命名体系が同時に存在し、`image`がどちらを指すのかを読み手が毎回判断することになる。既存フィールドの意味を変える一度きりのコストの方が安いと判断した。
- **`.masuda/images/<name>/`が存在すればエントリ名、無ければ従来のタグ名として解釈する折衷案**: 互換性を保てるが、1つのフィールドに2つの意味を持たせる暗黙の分岐であり、masudaが設定について暗黙の判断をしないというADR-0031以来の方針と噛み合わない。
- **`.masuda/Dockerfile`をエイリアスとして読み続ける**: 同じ役割のファイルが2箇所に正を持つ状態が残り、`masuda update`の書き換え対象もその両方を見る必要がある。ADR-0024が同じ状況で移行パスを持たない破壊的変更を選んだ前例に従った。
- **rootfsサイズをトップレベルの`.masuda/settings.json`の新フィールドにする**: メインVMのサイズはそこ、特権VMのサイズはコマンド宣言側、という分裂が起きる。サイズを決めているのはイメージの中身であり、それを定義するファイルの隣に置く方が対応関係が自明になる。
- **特権VM用イメージはmasuda自身が同梱し、対象リポジトリからはカスタマイズできない形にする**: ADR-0053がv1のスコープ外としていた元の想定。masudaのコード側に暗黙の推奨イメージを持つことになり、ADR-0031の原則に反する。またメインVMと特権VMでイメージの管理方法が異なる状態が固定される。
- **`masuda init`が特権コマンド用のエントリまで作り、ビルドは「参照されているエントリだけ」に絞る**: 使わないプロジェクトがビルドを負担しない点は`masuda image add`と同じだが、「宣言されたエントリは必ずビルドされる」という単純な規則が失われ、参照されていないテンプレートが全プロジェクトに転がることになる。使うと決めた人が明示的に1コマンド叩く方を選んだ。
- **サイズ指定を下限ではなく指定値そのものとして扱う**: 宣言値が中身より小さい場合に失敗するか使えないVMができるだけで、自動計算より優れた結果にならない。

## Consequences

- 破壊的変更である。既存の`.masuda/Dockerfile`と、`image`にDockerタグ名（`masuda-loop:go`等）を書いている`.masuda/settings.json`は、この変更後は機能しない。移行パスは提供しない
- 同梱の言語別バリアント（`docker/{go,python,typescript,full}`）を`image`フィールドで選ぶ経路が無くなる。ADR-0032がこれらの位置づけを「CI公開対象に加えるか、雛形生成方式に一本化して段階的に廃止するか、別途判断」として保留していたが、本ADRはその判断を強制する——バリアントは`.masuda/images/default/Dockerfile`の雛形バリエーションとして提供する形へ寄せる必要がある
- イメージが増えれば`masuda update`のビルド時間とローカルのディスク使用量が増える。特権VM用イメージはメインVMのイメージとレイヤーを共有しない（masudaのbaseから派生しない）ため、この増分は素直に加算される
- `masuda update`のFROM行書き換えが、ユーザーが独自に追加したエントリの`Dockerfile`にも及ぶ（masudaのbaseを参照する行だけ、という条件は従来と同じ）
- イメージディレクトリの内容を変更すると、そのイメージを使う特権コマンドの承認が失効し再承認が必要になる（ADR-0053のハッシュ固定）。Dockerfileの些細な修正でも再承認が要るという運用上の摩擦は、承認が実際に実行されるものを覆うことの対価として受け入れる
- rootfsサイズの上限をmasuda側の定数として持つため、正当に大きなイメージを必要とする対象リポジトリは、定数の変更（masuda自身のリリース）を待つことになる
