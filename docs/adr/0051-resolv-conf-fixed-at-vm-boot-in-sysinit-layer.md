# ADR-0051: `/etc/resolv.conf`の差し替えはVM起動時のoneshot unitで行い、systemd-resolvedと同じsysinit層に置く

## Status

Accepted (2026-08-19)

## Context

本ADRは Issue #11／#31 の作業中に下された判断を、`runtime/resolv-conf.service` のコメントとコードから再構成したものである。当時の議論の場に居合わせた記録ではなく、そこに残された記述と現在の実装から起こし直している。

VMゲストのrootfsは、Dockerイメージのファイルシステムをそのままext4へ変換したものである（[[0044-remove-docker-execution-runtime-vmbackend-only]]、`docs/design/images-and-rootfs.md`）。この中の`/etc/resolv.conf`は、`docker build`を実行したホストのコンテナ名前空間向けにDocker Engineが書いた内容（`# Generated by Docker Engine`、ビルドホスト自身のネットワーク名前空間にスコープされたnameserverアドレス。実機ではWSL2の内部NAT DNSプロキシで、他のどこからも到達できないことが確認されている）のまま焼き込まれている。

コンテナとして実行していた頃はこれが問題にならなかった。dockerdが`docker run`のたびに`/etc/resolv.conf`をbind mountで上書きするため、焼き込まれた内容は一度も使われなかったからである。しかしVMBackendのrootfsは焼き込まれたファイルシステムそのもので、VM起動時に`/etc/resolv.conf`を再マウントする主体が存在しない。この状態ではゲストはブリッジのサブネット外の名前を一切解決できない。

DNSサーバーのアドレス自体は既に供給されている。`runtime/vm-dhcp.network`のDHCPクライアントが、ホスト側dnsmasqから学習したDNSサーバー（ブリッジのゲートウェイIP）をsystemd-resolvedへ渡している（実機で`resolvectl status`により確認済み）。欠けているのは`/etc/resolv.conf`がresolvedのstubを指していないことだけで、これは`nsswitch.conf`の`dns`モジュール（`resolve`ではない）がdbus越しにresolvedへ問い合わせるのではなく、このファイルを直接読むためである。

## Decision

`runtime/resolv-conf.service`というoneshot unitをrootfsへ焼き込み（`Dockerfile:111`でコピー、`:123`で`systemctl enable`）、VM起動時に`/etc/resolv.conf`を削除して`/run/systemd/resolve/stub-resolv.conf`へのシンボリックリンクに差し替える。

```
ExecStart=/bin/sh -c 'rm -f /etc/resolv.conf && ln -s /run/systemd/resolve/stub-resolv.conf /etc/resolv.conf'
Type=oneshot
RemainAfterExit=yes
ConditionPathIsSymbolicLink=!/etc/resolv.conf
```

この unit は systemd-resolved と**同じ層**に置く。

```
DefaultDependencies=no
Before=sysinit.target systemd-resolved.service
[Install]
WantedBy=sysinit.target
```

`DefaultDependencies=no`＋`WantedBy=sysinit.target`は様式ではなく必須である（理由はAlternatives Consideredを参照）。systemd-resolved.service自身がこの2つを持っており、それに揃えている。

DNSサーバーのアドレス設定はこのunitの担当ではない。`runtime/vm-dhcp.network`のDHCPクライアントが行い、このunitは向き先の切り替えだけを行う。

## Alternatives Considered

- **Dockerfile内で`/etc/resolv.conf`を直す**: `docker build`のビルドコンテナ自身が`/etc/resolv.conf`をbind mountしているため、`RUN`ステップ内の`rm -f`ですら`Device or resource busy`で失敗する（実機で確認済み）。イメージがVMとして実際に起動した後でなければ触れない
- **`multi-user.target`層に置き、`Before=systemd-resolved.service`だけでresolvedと繋ぐ**: 当初この形だった。systemdがこれを順序循環として検出し、循環を解消するために**systemd-resolved.serviceの起動ジョブを黙って削除する**ため、resolvedがそもそも起動しなかった（実機で確認済み）。`sysinit.target`は暗黙に`multi-user.target`へ先行するが、`Before=`が「`sysinit.target`にWantedByされているresolved」に対して「`multi-user.target`層のunit」を待つよう要求する形になり、両立しない。resolvedと同じ層に置くことで、この衝突する暗黙の順序関係自体が消える

## Consequences

- ゲストはブリッジのサブネット外の名前を解決できるようになり、egressフィルタ（[[0045-redirect-over-tproxy-for-egress-interception]]）が前提とする「許可リストに無いホストのAレコードも普通に引ける」状態が成立する
- **失敗の出方が分かりにくい。** 2つ目の代替案で踏んだ順序循環は、エラーではなく「resolvedが起動しない」という結果としてのみ現れる。このunitの`DefaultDependencies=no`・`WantedBy=`・`Before=`のいずれかを変更すると、同じ形で再発しうる
- `ConditionPathIsSymbolicLink=!/etc/resolv.conf`により、既にシンボリックリンクであれば実行されない。再実行しても安全で、VM起動のたびに無条件で`rm`が走ることはない
- このunitはVM起動経路でのみ意味を持つ。`docker build`中もコンテナ実行時も systemd がPID1として動かないため実行されず、イメージのビルドには影響しない
