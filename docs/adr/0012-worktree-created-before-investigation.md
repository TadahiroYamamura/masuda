# ADR-0012: git worktreeの作成はフェーズ1（調査）より前に行う

## Status

Accepted (2026-07-25)

## Context

当初の設計（design doc初版）では、フェーズ1（調査）・フェーズ2（プラン作成）は「サンドボックス不要」という理由から、G1承認後・実装直前（旧フェーズ3）までgit worktreeを作らず、メインチェックアウトを直接読み書きする案だった。

しかし実装（ロードマップ2番、Go CLIの骨格）を終えてロードマップ3番（LangGraphオーケストレーターの6フェーズ化）に着手する段階で、以下の問題に気づいた。

- フェーズ1-2がメインチェックアウト直下に`INVESTIGATION.md`・`PLAN.md`を書く設計だと、これらはリポジトリ直下の単一ファイルになり、複数タスクの調査・プラン作成を同時に走らせられない
- G1で差し戻されて終わったタスクの後片付けが、worktreeベースの他フェーズと異なる特別扱いになる
- `masuda plan show|chat|approve|reject`は（G1時点でworktreeが存在しない前提だと）`masuda review show|chat|approve|reject <branch>`と異なるアドレッシング（`<branch>`引数の有無）が必要になり、CLIの一貫性が崩れる

これらはいずれも「サンドボックス不要」と「worktree不要」を同一視していたことに起因していた。worktreeの作成はホスト側のgit操作でしかなく、Dockerコンテナ（サンドボックス）を起動する理由にはならない。

## Decision

git worktreeの作成をフェーズ1より前（フェーズ0）に前倒しする。フェーズ1-2は、作成済みのworktreeに対してサンドボックスなしで（メインのClaude CodeセッションがホストOS上で直接Read/Grep/LSPし、サブエージェントに委譲する形で）実行する。Dockerサンドボックスの起動は引き続きフェーズ3（プロジェクト初期化、旧フェーズ4）まで行わない。

これにより「worktree作成のタイミング」と「サンドボックス起動のタイミング」を明確に分離した。

フェーズ番号は以下のように振り直す。

| 旧 | 新 |
|---|---|
| （worktree未作成） | 0: worktree作成 |
| 1: 調査 | 1: 調査（変更なし） |
| 2: プラン作成 | 2: プラン作成（変更なし） |
| 3: git worktree作成 | （0に前倒し） |
| 4: プロジェクト初期化 | 3: プロジェクト初期化 |
| 5: 実装 | 4: 実装 |
| 6: レビュー | 5: レビュー |

## Alternatives Considered

- **メインチェックアウト直読みのまま維持する**: フェーズ1-2の並列実行を最初から諦める設計になる。1リポジトリにつき同時に1タスクしか調査・プラン作成できないという制約を許容できるなら成立するが、複数タスクを並行して進めたいという利用シーンを狭めるため不採用。
- **G1だけ特別扱いのCLI（`<branch>`引数なし）にする**: [[0006-interactive-chat-plus-fast-path-gates]]で定めたゲート操作の一貫性が崩れ、実装・ドキュメントの両方で例外処理が増える。worktreeを先に作れば例外処理自体が不要になるため不採用。

## Consequences

- design doc「全体構成」のフェーズ表を0始まりに振り直した（旧フェーズ3が0、旧4が3、旧5が4、旧6が5）
- `masuda plan`・`masuda review`とも`<branch>`引数を取る、同一の実装（[[0006-interactive-chat-plus-fast-path-gates]]で定めたgate操作）をそのまま使い回せる。ロードマップ2番で実装済みのCLIに変更は不要だった
- フェーズ1-2で作られるworktreeは、G1で差し戻された場合も[[0005-manual-push-automatic-worktree-ops]]の自動worktree削除でそのまま後片付けできる
