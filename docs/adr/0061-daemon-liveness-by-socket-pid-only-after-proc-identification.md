# ADR-0061: 状態デーモンの生存判定はソケットへの接続で行い、PIDは`/proc`で同定してから停止にだけ使う

## Status

Accepted (2026-09-10)

## Context

[[0040-per-workspace-state-daemon-for-masuda-owned-state]]はデーモンのライフサイクルをワークスペース単位と定め、再開経路でも「PIDファイル＋signal 0（実際にはシグナルを送らない生死確認）で冪等に起動できるようにした——デーモンプロセスがホスト再起動や手動killで落ちていても自己修復する」とした。同ADRのConsequencesは、その自己修復が「次回のstart系コマンド実行まで」働かないことも認めている。

2026-09-09、その「次回のstart系コマンドが来ない」経路が実機で露呈した。G2（reviewゲート）で人間の判断を待っているワークスペースの最中に端末障害でホストが再起動し、`masuda review approve`が`connect: connection refused`で落ちた（Issue #52）。ゲートに座っているワークスペースには、定義上もうstart系コマンドが打たれない——次に打たれるのはapproveかrejectであり、そのどちらも`startDaemon`を呼ばない。ワークスペースは成果物を無傷のまま抱えたまま、承認も却下もできない状態で詰んだ。

調べる過程で、signal 0による判定そのものが再起動後には両方向に誤ることも分かった。ソケットのファイルは状態ディレクトリに残るが誰も待ち受けていない（接続はrefusedになる）。一方`daemon.pid`のPIDは、再起動でPID空間が巻き戻るため無関係なプロセスに再利用されうるが、signal 0は「その番号を誰かが持っているか」しか答えられない。この障害でPID 401012が空いていたのは、再起動から4分でPIDが4900番台までしか進んでいなかったという偶然にすぎず、設計上の保証ではなかった。

## Decision

PIDが担っていた2つの役割——「生きているか」と「誰を止めるか」——を分離する。

**生存判定はソケットへの接続で行う。** `daemonServing(stateDir)`（`cmd/masuda/statedaemon.go`）が`statedaemon.SocketPath(stateDir)`へ`net.DialTimeout`し、接続できれば生きている、それ以外は生きていないと判定する。PIDは一切見ない。呼び出し側が本当に知りたいのは「ソケットが応答するか」であり、それを直接聞く。`internal/sandbox.EnsureEgressProxy`が既にポートへのdialで冪等性を担保しており、masuda内で同じ形の2例目になる。

**PIDは停止させる相手の同定にだけ使う。** `isDaemonProcess(pid, stateDir)`が`/proc/<pid>/cmdline`（NUL区切りのargv）を読み、`statedaemon`と当該状態ディレクトリのパスが**それぞれ独立した引数として**現れることを確認する。`--state-dir <dir>`はディレクトリを別引数として渡すため、部分文字列一致にすると他ワークスペースのパスを前方一致で拾う余地が残る。`/proc`が読めない場合は「自分のではない」側に倒す。

`startDaemon`は「servingなら何もしない → そうでなければ`reclaimStaleDaemon` → 起動」の順になる。`reclaimStaleDaemon`は記録されたPIDが同定できた場合にだけSIGTERMして終了を待ち、同定できなければ（PIDファイル不在・プロセス死亡・PID再利用のいずれでも）何もしない——PIDファイルはこの後どのみち新しいプロセスのもので上書きされる。`stopDaemon`も同じ同定を通してからSIGTERMする。

あわせて呼び出し元を、デーモンを必要とする入口すべてへ広げた。`ensureGateWorkspace`（ゲート系7コマンドが必ず通る唯一の関数）、`sandbox start`（ゲストのmcp-relayがcuratedソケットを叩くため、VMだけ起こしてもループは進まない）、および`finalizeReviewApproval`からの`stopDaemon`（承認はワークスペースが終わるもう一方の経路であり、それまで状態ディレクトリだけ消してデーモンを残していた）。

## Alternatives Considered

- **dialを一次判定にし、失敗したらPID＋signal 0へフォールバックする**: 最初に採った案で、実装直前まで進んでから退けた。ソケットが応答せずPIDだけが生きている状態を「生きている」と答えるため、**まさにPID再利用のケースでIssue #52が直らない**。今回の障害で助かったのがPIDの空き具合という偶然だった以上、この案は問題を直したことにならない。
- **ソケットだけで判定し、応答しなければ無条件に起こし直す**: 「プロセスは生きているがリスナーだけ死んだ」場合に、同一のstoreに対して2つ目のデーモンが立つ。storeには書き込みの調停手段がなく「キーごとに単一ライター」が暗黙の前提のまま強制されていない（Issue #44）ため、応答しない1つのデーモンより悪い状態を作る。
- **デーモンにスーパーバイザを付ける（systemd user unit等）**: 「落ちても誰も気付かない」というADR-0040以来の構造そのものを解く根本案。ただし[[0055-gate-marker-is-an-unconsumed-decision-waited-on-by-presence]]が状態機械のホスト側移行を検討した際にもスーパーバイザの不在が却下理由の1つとして挙がっており、判断はそちらと一体で行うべき。本ADRは「呼ばれた時に自己修復する」という既存モデルを保ったままIssue #52を塞ぐことに範囲を限った。

## Consequences

- 生存判定がプロセスの存在ではなく到達性になったため、「プロセスは生きているが応答しない」デーモンも自動的に置き換わるようになった。反面、判定のたびにUDSへの接続試行が走る（タイムアウト1秒）
- `/proc`を読む同定はLinux固有。masudaはLinux専用なので現状問題にならないが、他プラットフォームへ移す際はここが最初に引っかかる
- 「読めない`/proc`は自分のではない」に倒した結果、同定できない状況ではデーモンがorphanとして残る。無関係なプロセスへSIGTERMを送る側の誤りより安いという判断であり、逆向きの誤りは他人のプロセスを殺す
- ゲート系コマンドがデーモンを起こすようになったため、`masuda review show`のような読むだけのコマンドでもデーモンプロセスが立ち上がる。ゲートの成果物はファイルとして直接読めるので原理的には不要だが、入口ごとに要否を判定する分岐を持つよりも、通る道を1本にする方を採った
- ADR-0040のConsequencesが挙げた「デーモンにスーパーバイザがなく、クラッシュしても次回のstart系コマンドまで気付かれない」という性質自体は解消していない。ゲートで待っている間にデーモンが落ちても、人間が次のコマンドを打つまで誰も気付かない点は変わらない
