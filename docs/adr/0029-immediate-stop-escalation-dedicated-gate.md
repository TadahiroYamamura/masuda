# ADR-0029: 最優先即時停止エスカレーション（層3）は全エージェントの自己申告で検知し、専用ゲート・人間専用コマンドで解決する

## Status

Accepted (2026-08-05)

## Context

GitHub Issue #4は、既存のエスカレーションをブロッキング（[[0010-plan-deviation-reopens-plan-gate]]、プラン逸脱）と非ブロッキング・記録型（[[0003-mechanical-vs-complex-review-nodes]]の横断的チェック、スコープ外の発見・代替案提案）に加え、セキュリティ上の懸念（プロンプトインジェクション等）を検知した際に最優先で即時停止すべき第3の層として整理することを決めていた。この層の具体的な検知責任者・実装方式は未決定のまま残っていた。

まず「誰が自己申告するか」を検討した。既存の観点別レビューエージェント（checker）に責任を持たせる案が最初に出たが、以下の理由で不適当と判断した。

- checkerはinvestigator・planner・implementerより後（各ステップの実装完了後、あるいはフェーズ5の全実装完了後）にしか呼ばれず、「最初に気付ける」という前提が構造的に成立しない
- checkerは[[0024-file-based-perspectives-mechanical-checker-prompt]]の設計によりdiffのみを見せられており、diffに含まれない既存ファイルの内容を読む機会がない
- インジェクションがレビューを欺く目的で仕込まれている場合、checker自身がその標的になりうる。標的にされたエージェントに自己申告を委ねるのは信頼性の観点で弱い

次に、[[0003-mechanical-vs-complex-review-nodes]]の横断的チェック（explorer→verifier）の軽量版を、[[0027-phase4-step-based-implement-review-commit-loop]]の途中レビューからステップ毎に呼び出す案を検討したが、これも不採用にした。

- 軽量化のためにexplorerの探索範囲・ターン数を絞ると、checker案と同じ「diffだけでは見えない」弱点を再現する
- コスト削減のためにプラン完了後の1回にまとめると、既存の非ブロッキング層（層2）と区別がつかなくなり、緊急性を理由に層3を新設する意味自体が失われる
- verifierを削って探索側だけ残す案も検討したが、verifierの呼び出しはexplorerが何か見つけた時だけ発生する（[[0003-mechanical-vs-complex-review-nodes]]と同じ条件付き実行）ため、通常時のコスト増はわずかで、信頼性を犠牲にしてまで削る理由がない

「即時性」を突き詰めると、この層が本当に検知したいのは「機械的バックストップ（[[0010-plan-deviation-reopens-plan-gate]]、変更ファイルの識別のみを見ており、diffの中身は一切見ていない）が原理的に見えない、内容レベルの異常」であり、かつ発見した瞬間に反応する必要がある。これを満たせるのは、専用の周期的チェック機構ではなく、その時点で実際に内容を読んでいるサブエージェント自身（investigator・planner・implementer・checker・横断的チェックexplorerのいずれでも）による、その場でのインラインな自己申告だけだと判断した。

なお「秘密情報の外部送信」はこの層で扱わない。サンドボックスのネットワーク制御で対処すべき別種のリスクであり、`internal/sandbox/sandbox.go`の`docker create`を確認したところ現状ネットワーク制限は一切設定されていないことが分かったため、GitHub Issue #11として別途切り出した。

検知方式が決まったところで、解決フローを検討した。[[0010-plan-deviation-reopens-plan-gate]]は「プラン逸脱専用の新しいゲート種別を作る」案を、[[0027-phase4-step-based-implement-review-commit-loop]]も同様に「途中レビュー未解決指摘専用の新しいゲート種別を作る」案を、共に「G1と本質的に同じ、AIの設計判断が正しいかを人間が舵取りするゲートだから」という理由で退け、既存のG1（plan）ゲートを再オープンする形に統一してきた。この層3についても同じ前例に倣うべきか検討したが、以下の理由で踏襲しないことにした。

- G1は既に「初回プラン承認」「機械的バックストップの逸脱」「（暫定策としての）途中レビュー未解決指摘」という3つの意味を1つのゲート名に背負っており、ここに4つ目の意味を足すとオーケストレーター側の分岐がさらに複雑化する
- G1・G2の`approve`/`reject`は二択で足りる（「この設計判断は妥当か」という一次元の問い）が、セキュリティ懸念は「誤検知だったので続行」「軽微なので手直しして続行」「深刻なので人間が手動点検するまで止める」など、二択に収まらない
- 何より、[[0010-plan-deviation-reopens-plan-gate]]・[[0027-phase4-step-based-implement-review-commit-loop]]が再利用してきたG1は「この設計判断は妥当か」という、AIの判断の質そのものを問うゲートである。一方この層3は「このエージェントの判断は（汚染された内容によって）そもそも信頼できるか」を問う、性質の異なるゲートである

この性質の違いは、ゲートの解決フローにも影響する。[[0006-interactive-chat-plus-fast-path-gates]]はゲートの解決手段として、chatで人間を納得させた上でClaude自身が承認マーカーを書く経路と、人間がホスト側から`approve`/`reject`を叩く経路の2つを対等な代替手段として用意している。G1・G2では「AIの判断の質」が論点なので、会話の末にAI自身が結論を記録することに問題はない。しかし層3では「このエージェントの自己申告・自己判断が信頼できるか」自体が論点であり、疑いの対象であるエージェントに、chatでの会話結果を理由に自分自身のゲートを閉じさせることは、この層が守ろうとしている独立した人間判断の経路を無効化してしまう。

## Decision

エスカレーション層3（最優先即時停止）を、G1（`plan`）・G2（`review`）とは別の専用ゲート種別として新設する。

- **検知**: investigate_plan_graph.py・implement_review_graph.py双方のどのサブエージェント（investigator・planner・implementer・checker・横断的チェックexplorer）からも、内容を読んでいる最中に懸念に気付いた時点でインラインに自己申告できる。専用の周期的スキャン機構は設けない
- **ゲート**: `.masuda-gate/triage.json`に書き出し、既存のGATE:\<name\>終了条件・inotifywait待機機構（[[0006-interactive-chat-plus-fast-path-gates]]、汎用設計のためランタイム側の変更は不要）に`GATE:triage`としてそのまま乗せる。G1（`plan`）・G2（`review`）がゲート名とCLIドメイン名詞を一致させている慣習に倣い、ゲート名もCLIコマンドと同じ`triage`にする
- **解決フロー**: `masuda chat`は懸念のあったエージェントとの対話・コンテキスト確認に使ってよいが、ゲートを閉じる最終判断は chat セッションの中でエージェントに書かせず、ホスト側から人間が独立して実行する専用コマンドでのみ記録する。この点で[[0006-interactive-chat-plus-fast-path-gates]]のchat自己解決経路とは意図的に異なる
- **CLIコマンド**: `masuda triage`を`plan`/`review`に続く3つ目のドメイン名詞として新設する（`masuda triage show`で懸念内容を表示、以下の3つの判断コマンドで解決を記録）。「問題への対応であること」「判断が要求されること」の両方を語彙自体が含意する`triage`（緊急度を判断して次の対応を決める、の意）を採用した
- **判断の選択肢**: `dismiss`・`redo`・`halt`の3つとする
  - `dismiss`（誤検知として続行）: そのステップの差分をそのままcommitして次へ進む。G1の`approve`と同じ意味論をそのまま流用する
  - `redo "<feedback>"`（対応した上でやり直し）: 人間が対処（該当ファイルの手直し・エージェントへの指示等）した上で、同じステップをfeedback付きで再実行する。G1の`reject "<feedback>"`と同じ意味論をそのまま流用する
  - `halt`（深刻・自動再開しない）: G1にもG2にも存在しない、層3固有の新しい選択肢。オーケストレーターのループ自体を終了させ、[[0011-iteration-budget-per-subagent-invocation]]の予算超過時の`DONE (blocked)`と同様の終端状態にする。**masuda側に自動的な再開経路は一切用意しない**——人間がhaltを選んだ時点で、AIに任せた結果復帰不可能な問題が発生した可能性を意味し、以降の修正は人間の手（ワークスペースを直接調査・修正するか、`workspace remove`で破棄するか）に委ねる、という判断による

[[0027-phase4-step-based-implement-review-commit-loop]]が暫定的に採用した「途中レビュー未解決指摘をG1再オープンで扱う」というエスカレーションは、セキュリティ由来の懸念に関してはこの新設ゲートに置き換わる。通常の観点レビューが自動修正ループで収束しない場合のG1再オープン流用は、本ADRの対象外として変更しない。

層2（非ブロッキング・記録型）は本ADRの対象外。[[0003-mechanical-vs-complex-review-nodes]]の横断的チェック（フェーズ5で1回、explorer→verifier）のまま変更せず、途中レビューへの拡張も行わない。

## Alternatives Considered

- **既存の観点別checkerを層3の唯一の自己申告責任者にする**: checkerは実装エージェントより後にしか呼ばれず、diffのみを見る設計（[[0024-file-based-perspectives-mechanical-checker-prompt]]）のため見落としが多く、加えてインジェクションの標的そのものになりうるため不採用
- **[[0003-mechanical-vs-complex-review-nodes]]の軽量版をステップ毎の途中レビューから呼び出す**: 軽量化により探索範囲を絞ればcheckerと同じ弱点を再現し、コストを理由にプラン完了後の1回に集約すれば層2と区別がつかなくなり層3を新設する意味が失われるため不採用
- **[[0010-plan-deviation-reopens-plan-gate]]・[[0027-phase4-step-based-implement-review-commit-loop]]の前例を踏襲し、G1再オープンをそのまま流用する**: G1は既に3つの意味を背負っており、approve/rejectの二択もセキュリティ懸念の多様な帰結を表現しきれない。何より層3が問うているのは「AIの判断の質」ではなく「エージェントの判断が信頼できるか」という別種の問いであるため不採用
- **[[0006-interactive-chat-plus-fast-path-gates]]と同じくchatでの会話の末にエージェント自身が承認マーカーを書く経路を許容する**: 層3の前提は「このエージェントの判断が汚染されているかもしれない」ことであり、疑いの対象自身にゲートの解決を委ねると、この層が提供しようとしている独立した人間判断の経路が無効化されるため不採用

## Consequences

- `halt`はmasudaのループ機構から見て終端であり、以後そのワークスペースを自動再開する経路は存在しない。人間が手動で調査・修正した上で改めて別の手段（直接のgit操作、新規ワークスペース作成等）を取る前提になる。これは意図的な設計判断であり、「halt後も自動復帰できる」ような救済コマンドを将来追加したくなった場合は、layer 3の存在意義（人間による独立判断を経ずに復帰させない）と矛盾しないか都度検討が必要
- [[0010-plan-deviation-reopens-plan-gate]]が確立した「ゲート種別を増やさず既存ゲートを再利用する」という方針からの初めての逸脱になる。今後さらに別種のエスカレーションを追加したくなった場合、同じ理由で新設が正当化されるかは都度個別に検討する必要がある
- `investigate_plan_graph.py`・`implement_review_graph.py`の両方から同じ新ゲートを発火できる必要があり、両オーケストレーターにまたがるゲート実装が必要になる（[[0010-plan-deviation-reopens-plan-gate]]の逸脱検知が既にフェーズ4側からG1を再オープンしている前例はあるため、実現可能性自体は確認済み）
- 秘密情報の外部送信対策（ネットワーク分離）は本ADRのスコープ外。GitHub Issue #11で別途追跡する
