# ADR-0013: G2（レビュー承認ゲート）の却下はフェーズ4（実装）を再オープンする

## Status

Accepted (2026-07-25)

## Context

フェーズ4（実装）とフェーズ5（レビュー）は同じDockerサンドボックス・同じ`runtime/CLAUDE.md`の自己ループ上で動く（ADR-0012の「サンドボックス起動とworktree作成は別タイミングでよい」と同じ理由で、フェーズ4-5は同一サンドボックスの中で連続して進む）。

既存のレビューグラフ（`feat/github-actions-langgraph-nodes`由来、13観点のreview/check往復）は、指摘そのものを自動修正するロジックを持たない。review/checkの往復は「AIの指摘（review）が正しいか（check）」を検証するためのものであり、指摘された問題を直すのは常にG2で人間が判断してから、というのが設計ドキュメント「フェーズ5（レビュー）の内部設計」の前提だった（機械的指摘のchecker/fixer自動修正ループは、今回のフェーズ5移植のスコープには含めず、ロードマップ4番に残した）。

この前提のまま実装を進めると、G2で`masuda review reject "<feedback>"`した場合に、そのフィードバックを消費して実装をやり直す仕組みが存在しないという抜けが見つかった。フェーズ4-5が同一サンドボックス・同一ループ上で動くことを踏まえると、G2却下は「実装フェーズに戻ってやり直す」という形で扱うのが自然である。

## Decision

G2の却下は、新しいゲート種別を作らず、フェーズ4（実装）を却下フィードバック付きで再実行する形で扱う。これは[[0010-plan-deviation-reopens-plan-gate]]の「G1再オープン」と同じパターンをG2に適用したものである。

フェーズ4とフェーズ5は1つのオーケストレーター（`orchestrator/implement_review_graph.py`）にまとめ、両フェーズ間の遷移を内部の状態遷移として扱う。具体的な流れ:

```
フェーズ4（実装） → フェーズ5（レビュー: review/checkの往復→synthesize）
  → G2待機（終了、人間の判断待ち）
  → 却下（feedback付き）
      → フェーズ4を却下フィードバック付きで再実行 → 再度フェーズ5 → ...
  → 承認
      → `masuda review approve`がローカルmerge・worktree削除まで自動実行（既存通り）
```

## Alternatives Considered

- **G2却下からG1（プラン承認ゲート）に戻す**: レビュー指摘の多くは実装レベルの修正であり、プランそのものを見直すほどの逸脱ではないケースが大半。G1まで遡るのは過剰な手戻りになるため不採用。
- **G2却下専用の新しいゲート種別を作る**: [[0010-plan-deviation-reopens-plan-gate]]で却下した理由と同じで、ゲート種別を増やすと運用が複雑になるため不採用。

## Consequences

- `implement_graph.py`と将来のレビューグラフを別々の独立したオーケストレーターとして設計する案は採用しない。フェーズ4-5は1つのオーケストレーターにまとめる（ファイル名を`implement_graph.py`から`implement_review_graph.py`に変更）
- G2は一度きりのゲートではなく、レビュー指摘の却下によって再オープンされうるものとして設計する必要がある（G1と同じ性質）
- 却下フィードバックを反映した再実装後は、レビューをフェーズ0からやり直す（前回のreview/check結果は使い回さない）。指摘に対する修正が本当に妥当かは、レビューをゼロからやり直して確認するのが安全なため
