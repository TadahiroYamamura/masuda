# ADR-0002: メインエージェントはワークフロー管理に専念し、実作業はサブエージェントに委譲する

## Status

Accepted (2026-07-25)

## Context

`feat/github-actions-langgraph-nodes`ブランチのCLAUDE.mdには「サブエージェントへの委譲方式を廃止し、LangGraphの直接API呼び出し方式に移行した」という記述がある。撤退理由は「サブエージェントへの委譲ではトークンのコストが管理しきれなかった」ため。

[[0001-self-loop-over-direct-api]]でサブスクリプション認証の自己ループに全面移行することを決めたため、この撤退理由（トークンコスト管理）は前提として成立しなくなった。

一方、`develop`ブランチのPoCは1つの継続的なtmuxセッションが全ステップ（TASK.mdの読み込みから実際の作業まで）を自己完結して行う構造になっている。これをそのままレビューや実装のような大量の観点・ステップを持つ処理に適用すると、1セッションのコンテキストに全ての作業内容が積み上がり続け、長時間のループでコンテキストが肥大化・ドリフトするリスクがある。また、1セッション=1モデルのため、観点ごとに異なるモデル階層（例: reviewは上位モデル、checkは軽量モデル）を使い分けることもできない。

## Decision

メインエージェント（tmux上で自己ループするClaude Codeセッション）はワークフロー管理役に専念する。具体的には、TASK.mdの読み書き、LangGraphオーケストレーターの起動タイミングの判断、サブエージェントへの作業委譲と結果の検証のみを行う。実際の調査・プラン作成・実装・レビューはすべて、その都度起動する別コンテキストのサブエージェントに委譲する。

サブエージェントの成果物はJSONファイルとして書き出させ、メインエージェントがスキーマを機械的に検証してから次のステップに進む（[[0001-self-loop-over-direct-api]]で失われた「保証」の代替）。

## Alternatives Considered

- **`develop`ブランチのPoCと同様、1つの継続的なセッションが全作業を行う**: シンプルだが、長時間ループでのコンテキスト肥大化・ドリフトのリスクがあり、観点ごとのモデル階層の使い分けもできないため不採用。

## Consequences

- コンテキストが用途ごとに分離され、メインループのコンテキストが小さく安定した状態を保てる
- サブエージェント呼び出し単位でモデルを指定できるため、reviewer/checkerのモデル階層分離（直接API方式が持っていた性質）をむしろ再現しやすくなる
- サブエージェントの完了報告を鵜呑みにできない（[[0001-self-loop-over-direct-api]]参照）ため、ファイル経由の検証ステップが必須になる
- レビュー用サブエージェントに渡すツール権限は用途ごとに絞る必要がある（例: diff以外を見せない）。これによりレビュー範囲を確定的に保つ設計方針は維持されるが、観点によっては広い権限が必要になる（[[0003-mechanical-vs-complex-review-nodes]]参照）
