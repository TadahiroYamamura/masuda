# コーディング

## 想定外の状態の扱い

「ありえない状態」でも、エラーを値として返さずに処理を中断させる実装（Go の `panic`、comma-ok なしの型アサーション、Rust の `unwrap` 等）は提案しない。エラーを返し、呼び出し元で扱わせる。

- 背景: これらは recover されなければプロセスごと終了し、recover されても呼び出し元はエラーとして扱えない。めったに通らない経路（E2E で通らない等）にあると、バグに気づかないままリリースされる
- 戻り値でエラーを返せない場所では、少なくともエラーログで検知できるようにする。黙って握りつぶさない
- 「既存コードがそう書いていた」はこの実装を残す理由にならない

## 依存の追加

- 新しい依存パッケージを追加する前にユーザーに確認する

## 早すぎる抽象化を避ける

- 構造的な解決（型の追加・汎用化・設定項目の追加）より先に、既存コードの最小差分で足りないか確かめる
- 「将来の拡張性」は抽象化の根拠にしない。そのケースが実際に来るかを確かめる

## 用語

- 画面・仕様書・既存ドキュメントで使われている語を使う。コードを読み解く過程で自分が名付けた言葉を、命名・コメント・テスト名・コミットメッセージに持ち込まない
